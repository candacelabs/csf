## 3. Ruling on `Bind.Fields` — DEV-1 is right, QA-1 is overruled

QA-1's §6 recommended keeping `Fields` element-scoped while moving `Debounce`
and `Throttle`. DEV-1 moved all three. **The project needs one of these on the
record and it is this one: `Bind.Fields` belongs to the binding.** Three grounds,
in the order I would defend them.

**1. QA-1's own distinction decides it against QA-1's conclusion.** The
recommendation's ground is that `fields()` reads the element anyway — its form,
its `name`, its `value`. That is true and it is untouched: `fields(el, st)` still
reads all of it off `el` (`client/runtime.js:570`–`:584`). But that is **what the
element contributes**, and it is the same for every binding on it because it *is*
the element. `Bind.Fields` is not that. It is a value the author wrote **inside
one `OnWith` call**, and two `OnWith` calls on one element are two authors. The
distinction QA-1 drew is exactly the distinction that says `Bind.Fields` moves.

**2. The counter-case is not hypothetical, it is a frozen requirement.**
`F-CTR-6` is two keys on one focused element raising `+1` and `−1`. Today those
are two *different* event names. The moment they are one name with a `dir` field
— which is the ordinary way to write it, and the way `bench/README.md` G-10
describes the shape — element-scoped `Fields` under first-wins sends the second
binding **the first binding's payload**, silently. That is failure 2 with a
different symptom.

**3. "A rule with one unpredictable exception is worse than either rule" is
correct, and it is load-bearing later in this document.** *An option a binding
declares scopes to that binding* is a rule a reader can carry. *…except `Fields`,
which is element-scoped for a reason about a different function* is a rule
nobody can predict from the type. I hold DEV-1 to this in §10, where I refuse a
`Modifiers` shape on the same ground — and I would not ratify the principle here
and abandon it there.

**Recorded because the recommendation was right about half of it and that half
survived**: nothing about `fields()`'s element half moved, and `2ab18690` says so
in the commit body and in `client/SIZE.md` §7 rather than letting the overrule
read as a rejection of the whole note.

## 4. FR54-1 — *"there is no mixed-version window"* is false, and I drove it

`docs/api-surface.md:586`, last row of the new §10 section:

> The only exported behaviour that changed is the markup `On`, `OnWith` and
> `OnAll` emit, which is `client/SIZE.md` §7's contract and is versioned with the
> runtime that reads it: both ship in the same binary, embedded by exact
> filename, **so there is no mixed-version window**.

The premise is true and the conclusion does not follow. The runtime is served at
`<mount>/gotth-live.min.js` — **a path with no build fingerprint** — with
`Cache-Control: public, max-age=31536000, immutable` (`live/templ.go:627`). A
browser that fetched the runtime before the upgrade will not revalidate it for a
year, and `immutable` tells it not to revalidate on an ordinary reload either.
**The two artifacts ship in one binary; they do not arrive at one browser.**

Driven rather than derived. `client/runtime.js` at `2ab18690^` (54,007 B),
against markup HEAD renders today, in the committed node harness:

```
OLD runtime + NEW markup
  armed timers: 0  | events on the wire: ["c.draft"]     ← the declared 150 ms debounce is gone
  event: f.one     | fields delivered: []                ← Bind.Fields{room:"alpha"} is gone
```

Both specs red. No error, no console warning, no `4003`. A page that asked for a
150 ms debounce sends a frame per keystroke — which is `FRICTION.md` F-3's own
defect — and an event that declared a static field arrives with **no fields at
all**, which can change what the reducer does rather than merely how often.

**And the deployment guide already reasons about this, and its reassurance is
now wrong.** `docs/guide/deploying.md:54`–`:56`:

> Within a protocol major version that is usually harmless: an old runtime and a
> new server still speak `gotth-live.v1`, and the version check that would close
> the session (`4003 UNSUPPORTED_VERSION`) only fires on a **major** mismatch.

That paragraph is about the **wire protocol**. `client/SIZE.md` §7 is a *second*
contract between the same two parties, the protocol version does not cover it,
and `4003` cannot catch it. This landing changed the second contract while the
first stayed at v1 — so this is the first upgrade for which "usually harmless" is
exactly wrong, and it is wrong **quietly**, which is this project's own criterion
for what may not be left to the caller.

> **FR54-1 (blocking, §9.7).** The sentence at `api-surface.md:586` is corrected
> — beneath itself, not by rewriting, per this section's own convention. I have

## 5. `OnAll`'s replacement property — probed, and it holds

The old rule ("where two bindings disagree the first wins") existed so that
moving a page from two spreads to one `OnAll` could not silently change which
debounce was in force. The godoc now claims something stronger: **a binding
rendered by `OnAll` is byte-identical to that binding rendered alone.**

A throwaway module in the container's `/tmp`, `replace`d onto the mounted
worktree, using only exported API. Eight shapes covering every component and
every combination of set and unset:

```
On(click,c)                                  -> "click:c"
OnWith(input,i,{D:150ms})                    -> "input:i::150"
OnWith(keydown,k,{Keys:[Escape]})            -> "keydown:k:Escape"
OnWith(keydown,k,{Keys:[+,-],F:{dir:up}})    -> "keydown:k:+:::dir=up;keydown:k:-:::dir=up"
OnWith(scroll,s,{T:200ms})                   -> "scroll:s:::200"
OnWith(x,y,{F:{a:1}})                        -> "x:y::::a=1"
OnWith(a,b,{D:1ms,T:2ms,F:{q:r},Keys:[A,B]}) -> "a:b:A:1:2:q=r;a:b:B:1:2:q=r"
OnWith(sub,ms,{D:500us})                     -> "sub:ms::0"

OnAll of all eight   BYTE-IDENTICAL CONCATENATION: true
every ordered PAIR   pairs checked = 64, mismatches = 0
NEGATIVE CONTROL     got==wrong: false
non-attrOn merge     map[class:first data-gotth-on:click:a;click:b]
```

**PASS.** The property is not merely true, it is true *by construction*:
`binding()` joins a key list with `;` and `OnAll` joins bindings with `;`, so
composition is concatenation and there is nothing left that could disagree. The
negative control is what makes the 64 mean something — it is the same comparison
with one byte appended, and it printed `false`.

Two things worth recording beside the pass. `OnWith(sub,ms,{D:500us})` renders
`"sub:ms::0"` — a sub-millisecond interval becomes `0`, which the client reads as
none; that is unchanged behaviour and the `binding` godoc states it. And the
first-wins carry-through for **non**-binding attributes survives (`class:first`),
which is the defensive half the godoc says it is.

## 6. FR54-3 — the positional grammar, attacked

Thirty hostile inputs through the real helpers, then re-split exactly as
`dispatch` splits. The good news first, because three of the four things the
brief asked me to attack came back clean.

**`Fields` cannot split the grammar it sits in. Confirmed, not assumed.**
`encodeFields` is `net/url`'s query encoding and it escapes both separators in
**keys and values alike**:

```
Fields{a: "x:y"}        -> "click:e::::a=x%3Ay"
Fields{"k:1": "v;2"}    -> "click:e::::k%3A1=v%3B2"
Fields{a: "1:2:3:4:5"}  -> "click:e::::a=1%3A2%3A3%3A4%3A5"     one component, always
```

And the spec that owns it can fail: mutating `encodeFields` to un-escape `%3A`
and `%3B` turns **exactly one** spec red — *"percent-encodes a field whose value
would otherwise split the binding"* — 283 passed, 1 failed.

**An empty component in the middle means "not set", consistently, on both
sides.** `+"" === 0`, `+undefined` is `NaN`, `NaN || 0` is `0`, so a trimmed
binding and a placeholder binding read the same. Verified for a throttle without
a debounce (`scroll:e:::200` → `d=""`, `th="200"`), fields alone, a negative
`Debounce` (omitted), an empty `Fields` map (omitted) and an explicit
`Keys{""}` (renders as no key component at all — the documented "every key").

**The unbindable set really is unchanged, and every other printable key survives
the new components.** `,` `+` `-` ` ` `|` `=` `&` `%` `"` `<` all round-trip into
the key slot untouched. The godoc's claim at `live/templ.go:158`–`:167` — still
`:` and `;`, and no character taken away — **is true**.

**And here is what is not true enough.** The set of characters a key may not be
did not grow. **The penalty for using one did**, and this landing is what grew
it:

| call | before `2ab18690` | at HEAD | what the client does at HEAD |
|---|---|---|---|
| `Bind{Keys:[":"]}` | `keydown:e:` | `keydown:e::` | filter widens to **every key** (unchanged) |
| `Bind{Keys:[":"], Debounce:150ms}` | `keydown:e:` + `data-gotth-debounce="150"` | `keydown:e:::150` | filter widens **and `d=""`, `th="150"` — the debounce is now a throttle** |
| `Bind{Keys:[";"], Debounce:150ms}` | `keydown:e:` + the attribute | `keydown:e:;:150` | splits into **two** specs: `keydown:e:` (unfiltered, unencumbered) and `:150` (junk) |

Before this landed, an unbindable key widened the filter and the debounce still
worked. Now it widens the filter **and moves every later option one slot left**.
Nothing rejects it, nothing warns, and the author wrote something the godoc told
them was impossible and got a third behaviour neither of them named.

> **⟨CORRECTED 2026-08-05 — the direction in the sentence above is backwards,
> and DEV-1 caught it. Kept for the record, per this document's own
> convention.⟩** An unbindable key **inserts** a component, so every option
> behind it lands one slot **later** — to the **right**, not the left.
> `Keys{":"}` + `Debounce{150ms}` renders `keydown:e:::150`, which splits to
> `["keydown","e","","","150"]`: the `150` the author wrote for component 4
> (debounce) arrives at component 5 (throttle). The table directly above states
> the effect correctly (`d=""`, `th="150"`); only this prose sentence has the

> later"*, which is right. Ruled at §20 (C-1 row) and §21.1.

The same shift reaches a second way in, and it is easier to hit: **nothing
validates `domEvent` or `eventName` either.**

```
On("click","a:b")            -> "click:a:b"     name="a", key="b"; a click has no e.key,
                                                so this binding NEVER fires
OnWith("click","a:b",{D:150})-> "click:a:b::150" …and 150 lands in the throttle slot
On("click","a;b")            -> "click:a;b"     two specs, the second junk
On("click","")               -> "click:"        matches, name="" -> `if (!name) return`
                                                — AND it `break`s first, so it SHADOWS
                                                any later binding for the same DOM event
```

The last one is the sharpest: `dispatch` breaks out of the match loop on the
first spec whose `s[0]` matches and whose key filter passes, and only *then*
tests `name`. A binding with an empty event name therefore silences every
binding behind it on the same DOM event, in silence. That one predates this
landing; the option-shift does not.

>

> **FR54-5 (non-blocking).** `Bind.Keys`' godoc says `:` and `;` "cannot be

# Part B — the ruling on failure 1

## 10. Both refusal arguments on the record are aimed at the wrong target

§5.6 records two, PM-1 calls them *"real refusal arguments"*, and I have to
report that **neither of them refuses the thing `F-CHT-3` asks for.** This is the
whole reason the item has sat undecided for three revisions: the arguments read
as sufficient and are about a different case.

### 10.1 *"A chord belongs to the browser"* — true of three modifiers, and `F-CHT-3` names the fourth

The argument is stated in `live/templ.go:148`–`:153` and `client/runtime.js:648`–
`:652`, and it is correct about `Ctrl`, `Meta` and `Alt`: those chords are claimed
by the browser and by the operating system, this runtime calls `preventDefault`
for a key never, and a filter that matched one would raise an event while the
browser went on doing its own thing anyway.

**`Shift+Enter` in a `<textarea>` is none of that.** No browser reserves it; no
operating system claims it; the browser's own default for it is *insert a line
break*, which is the same default bare `Enter` has. Nothing is being taken over.
It is ordinary text editing.

The godoc's other half is the one that actually bounds the gap, and it bounds it
much more narrowly than the argument implies: **`KeyboardEvent.key` already folds
`Shift` into every printable value.** `Shift`+`=` arrives as `"+"`, which is
exactly why `F-CTR-6` passes today with no modifier surface at all. So the gap is
not "modifiers"; it is precisely and only **"distinguish `Shift` on a
non-printable key"**, and of those, the only one any consumer here wants is
`Enter`.

**Verdict: the argument is kept and narrowed to where it is true.** It refuses
`Ctrl`/`Meta`/`Alt` chords, and §12 refuses them on it. It does not reach the
requirement.

### 10.2 *"A library that `preventDefault`s on the application's behalf takes over `Ctrl+F`"* — true of a default nobody proposed

`client/runtime.js:679` already calls `preventDefault`, today, for two cases:

```js
if (e.type === "submit" || (e.type === "click" && el.tagName === "A")) e.preventDefault();
```

Both are cases where **the application declared a binding on that element for
that event** and sending it over the socket *is* the action. The library is not
guessing; it is honouring a declaration.

*"On the application's behalf"* is the load-bearing phrase and it describes a
library that suppresses defaults the application did not ask about — which is
what an *unconditional* `preventDefault` on every key binding would be, and it
would indeed eat `Ctrl+F` on any element with a `keydown` binding. **An opt-in,
per binding, defaulting off, written by the author beside the key they named, is
the submit case and not the `Ctrl+F` case.**

**Verdict: the argument refuses a design nobody has proposed. It does not reach
an opt-in.**

### 10.3 Quiet-versus-loud — I applied the project's criterion, and it does not decide this

The precedent is `docs/reviews/page-shell.md:529` and the countersignature it
cites: *the one shrink this project took was taken because its failure is loud*,
which is why `Config.Init` shrank while the security bundle stayed refused.

Applied honestly, **`F-CHT-3`'s failure is loud.** Press `Shift+Enter` once and
the message sends. Press `Enter` once and the newline appears *beside* the send.
Neither can lurk; both show up on the first interaction, in the developer's own
manual test.

**And the criterion still does not license refusing this, because loudness was
doing a specific job in that precedent that it cannot do here.** It made it safe
to leave the thing *to the caller* — a caller who noticed could repair it **inside
the library's vocabulary**. Here the caller who notices has no repair inside the
vocabulary at all: the only remedy is hand-written JavaScript on the element,
which is the exact thing FR-54's own text — *"bindings expressible from templ
with no hand-written JS"* — exists to prevent. Loud-but-unremediable is not the
shape the criterion was built for, and stretching it to cover this would turn it
into *"any failure a developer can see may be refused"*, which is every failure.

**So I am not borrowing its authority. What decides this is the price, measured,
of exactly the requirement's own case.**

### 12.1 The accepted shape — specified so DEV does not re-decide

```go
type Bind struct {
	Fields   map[string]string
	Debounce time.Duration
	Throttle time.Duration
	Keys     []string

	// NoModifiers restricts this binding to key presses with NO modifier key
	// held — no Shift, no Control, no Alt, no Meta.
	//
	// False, the zero value, is what every key binding has meant since
	// 591c275a: the key is compared and the modifier state is not. That
	// default is not a legacy, it is required: a printable key already
	// carries its modifiers, and "+" IS Shift and "=" on most layouts, so a
	// binding that named "+" and silently demanded no modifier would match
	// nothing (F-CTR-6).
	//
	// It has no effect on a binding with no Keys, and none on an event that
	// carries no key.
	NoModifiers bool

	// PreventDefault calls preventDefault() on the browser event when THIS
	// binding matches, and only then.
	//
	// The library calls it for a recognised form submit and an anchor click
	// already; this is the same act for a binding the author declared
	// explicitly, per binding, defaulting off. It is not a filter: a binding
	// that does not match does not suppress anything, which is what leaves
	// Shift+Enter to the browser.
	PreventDefault bool
}
```
