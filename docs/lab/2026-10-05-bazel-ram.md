# 2026-10-05: Bazel sandbox trees in RAM (BAZEL-RAM, #345)

Question: does moving Bazel's per-action sandbox directories onto a tmpfs
(`--sandbox_base=/dev/shm`) make `tools/bazel.sh` builds faster or lighten the
host's I/O pressure?

Verdict: **no measurable win; nothing lands.** `.bazelrc` and
`tools/bazel.sh` are unchanged. Every RAM configuration's spread overlaps
today's defaults, and the pooled medians differ by 0.45 s on a 57 s build.

## What Bazel actually runs

In the wrapper's container Bazel uses the process-wrapper sandbox, not
linux-sandbox. Every build's summary line:

```
INFO: 1940 processes: 512 internal, 1428 processwrapper-sandbox.
```

linux-sandbox is not registered at all. Asking for it fails:

```
ERROR: 'linux-sandbox' was requested for explicit default strategies but no
strategy with that identifier was registered. Valid values are: [dynamic_worker,
processwrapper-sandbox, standalone, dynamic, remote, worker, sandboxed, local]
```

The reason is that Bazel's probe of the `linux-sandbox` binary fails. The same
binary, run in the same unprivileged container, prints:

```
src/main/tools/linux-sandbox.cc:200: "clone": Operation not permitted
```

Docker's default seccomp profile refuses namespace creation to a container
without `CAP_SYS_ADMIN`. A session container from SESSION-CONTAINER (#325) is
the same kind of container, so it will make the same choice.

## Flags in Bazel 9.2.0

- `--sandbox_base` takes a path for the sandbox directories.
- The reuse flag is spelled `--[no]reuse_sandbox_directories`, and it
  **defaults to true** (`bazel help build --long`). Configuration C, which is B
  plus `--reuse_sandbox_directories`, is therefore the same configuration as B.
  To measure what reuse contributes, a fourth configuration, Bnr, runs B with
  `--noreuse_sandbox_directories`.

## `--shm-size` alone does not work

Docker mounts `/dev/shm` with `noexec`, whatever `--shm-size` says:

```
shm /dev/shm tmpfs rw,nosuid,nodev,noexec,relatime,size=1048576k,inode64 0 0
```

rules_go's builder executes a tool from inside the sandbox tree, so the first
round of B, C and Bnr (5 runs each, `--shm-size 16g`) failed every time after
121 actions:

```
GoStdlib external/rules_go+/stdlib_/pkg failed: (Exit 1): builder failed
filterbuildid: permission denied
```

The round that was measured mounts `/dev/shm` as
`--tmpfs /dev/shm:rw,exec,nosuid,nodev,size=16g` instead. Any future attempt
needs an exec tmpfs too. That is Docker's `HostConfig.Tmpfs`, not
`HostConfig.ShmSize`.

## Method

- **Target set:** `bazel build --keep_going //pkg/... //services/... //app/...`.
  This is the whole handwritten Go tree with its test binaries: 1,940 actions,
  1,428 of them sandboxed (`GoCompilePkg`, `GoLink`, `GoStdlib`). It is the set
  sessions build most often, and almost every action is sandboxed.
- **Cache state:** a private output base with no disk cache, so no action is
  served from cache. External repositories were warmed once by a discarded
  build. `bazel clean`, which keeps external repositories, ran before every
  measured build.
- **Order:** the configurations were interleaved round-robin (A, B, C, Bnr) for
  5 rounds, so host noise from other sessions lands on all of them alike. A was
  measured in 5 more interleaved runs during the noexec round, where its
  configuration was identical, which gives n=10.
- **Wall:** from the wrapper's start to its exit, including the container and
  Bazel server start, and analysis.
- **I/O pressure:** `/proc/pressure/io` `full avg10`, sampled every second
  during the build. The table gives the mean of each run's samples.
- **Memory:** the build container's cgroup `memory.peak`, which includes page
  cache, and the peak of `anon` from `memory.stat`.
- **`/dev/shm` use:** the peak of `df /dev/shm` inside the container, sampled
  every second.
- **Host:** 32 vCPU, 67 GB RAM, other sessions building at the same time.

## Why the win is not there

- The best run of A and the best run of B are both 48.0 s. The build is bound
  by compile and link CPU on the critical path, not by building symlink trees.
- During A builds, host I/O pressure (`full avg10`) had a median of about 1%.
  The 9% that motivated the ticket was measured while four sessions built at
  once. A single build's symlink trees are small writes that the page cache
  absorbs.
- Moving the trees to RAM costs about 1.4 GiB of RAM per building session and
  returned nothing measurable.
- Turning reuse off (Bnr) did not show a clear loss either: its median is
  slower, but its spread covers A's. Reuse is the default already, so there is
  nothing to change.

## shm size, if a later measurement ever wins

- **Peak:** the largest measured `/dev/shm` use is 1.46 GiB, across all 10 B and
  C runs. Run-to-run variation is small: the median is 1.42 GiB.
- **Margin:** ×1.5, the same headroom the session-container memory limit uses
  for build peaks. Target sets outside the Go tree (the OCaml compiler, the Rust
  workspace) were not measured. 1.46 × 1.5 = 2.19 GiB, rounded up to 2.25 GiB
  (`size=2304m`).
- **Check against RAM:**
  - The harness admits at most cores − load1 sessions, which is 32 on this host.
  - 32 × 1.46 GiB of measured peak is 46.7 GiB. About 47.5 GiB was available,
    so all sessions building at their peak at once would nearly exhaust memory.
  - 32 × 2.25 GiB of caps is 72 GiB, more than the host's 62.4 GiB.
  - tmpfs is allocated lazily, so a cap is not a reservation. The size is safe
    only while concurrent builds stay below about 20.
- **Inside a session container:** tmpfs pages count against that container's
  memory limit (9 GiB in SESSION-CONTAINER). Measured anon plus shm is
  4.3 + 1.5 = 5.8 GiB, which fits.

Since nothing won, the size SESSION-CONTAINER should give session containers
for Bazel is none: keep Docker's default `/dev/shm`.
